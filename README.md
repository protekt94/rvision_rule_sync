# rvision-rule-sync

Локальная CLI-утилита для сопровождения кастомных правил **R-Vision SIEM**.
Сравнивает актуальные кастомные `.ro` с соответствующими `RV-*` из пакетов `.roc`,
показывает структурный diff и выделяет отмеченные пользователем критичные изменения.

Основной сценарий: положить свои правила в `custom/`, новые пакеты в `SIEM/`
и выполнить `rvision-rule-sync compare --custom-prefix SOC-`. Префикс
задаётся пользователем; `SOC-` здесь приведён как пример. История версий и предварительная регистрация
правил для этого не нужны.

Утилита работает офлайн. Она не использует LLM, не подключается к SIEM API,
не исполняет VRL и не импортирует правила. Это независимый проект, не официальный
инструмент R-Vision.

## Возможности

- Распаковка ZIP, TAR и сжатых TAR с расширением `.roc`.
- Рекурсивный поиск `.ro` и сопоставление по полю `id`: `<custom-prefix><suffix>` → `RV-<suffix>`.
- Парсинг YAML с сохранением многострочных `!vrl`, включая вложенные фильтры.
- Сравнение `metadata`, `filter`, `aliases`, `select`, `group`, `ttl`,
  `throttle_time_sec`, `on_correlate` и неописанных полей.
- Исключение верхнеуровневых `test` и `tests` из diff и статусов.
- Отдельное отображение фрагментов между маркерами «моих изменений».
- Markdown-отчёт, JSON-результаты и снимки входных правил для каждого запуска.
- Дополнительный трёхсторонний анализ BASE/OURS/THEIRS с консервативным слиянием.

## Требования и установка

Python **3.10+**. Единственная зависимость во время работы — PyYAML.
Для тестов дополнительно нужен pytest.

Скачайте или клонируйте этот репозиторий и откройте терминал в его корне.

### Linux / macOS

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
```

### Windows PowerShell

```powershell
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -e .
.venv\Scripts\rvision-rule-sync.exe --help
```

В PowerShell далее можно использовать `.venv\Scripts\rvision-rule-sync.exe`
вместо `rvision-rule-sync`; активация окружения не обязательна.
Альтернативный запуск после установки: `python -m rvision_rule_sync`.
Установка зависимостей может требовать сеть; сама утилита сетевых запросов не делает.

## Быстрый старт

```text
rvision-rule-sync/
├── custom/
│   ├── SOC-D-100.ro
│   └── SOC-D-200.ro
├── SIEM/
│   └── new-content.roc
└── reports/                 # создаётся автоматически
```

```sh
rvision-rule-sync compare
```

В терминале команда сначала спросит префикс, например `SOC-` или `COMPANY-`.
Затем она читает `custom/` и `SIEM/` относительно текущего каталога и выводит путь
к новому `report.md`. Содержимое custom не меняется. Если правило изменено в SIEM,
замените соответствующий файл его актуальным экспортом. Новое правило достаточно
добавить в `custom/` — `bootstrap` для compare не нужен.

Можно указать другие пути, один пакет или шаблон:

```sh
rvision-rule-sync compare --custom-prefix SOC- --custom ./my-rules ./SIEM/new-content.roc
rvision-rule-sync compare --custom-prefix SOC- --custom ./my-rules "SIEM/*.roc" --output ./reports
```

Windows-шаблон `"SIEM\*.roc"` также поддерживается. Папка SIEM просматривается
без рекурсии; `.ro` в папке custom ищутся рекурсивно. Имена файлов правил могут быть
произвольными — используется `id` внутри YAML.

Если пакетов несколько, каждое custom-правило сравнивается **с каждым пакетом отдельно**.
Правила разных пакетов не смешиваются. Утилита не выбирает «самый новый» пакет по
имени или времени файла: для одного обновления передайте его путь явно.

### Выбор префикса

Префикса по умолчанию нет. Укажите его явно:

```sh
rvision-rule-sync compare --custom-prefix COMPANY-
```

Это сопоставляет `COMPANY-D-100` с `RV-D-100`. Другой пример — правила с префиксом `CUSTOM-`:

```sh
rvision-rule-sync compare --custom-prefix CUSTOM-
```

Можно ввести `SOC` вместо `SOC-`: завершающий дефис добавится автоматически.
Поддерживаются составные префиксы, например `ACME-SOC-`, и подчёркивания:
`MY_TEAM-`. Префикс начинается с латинской буквы, далее допустимы латинские буквы,
цифры, `_` и `-`. Регистр значим. `RV-` и начинающиеся с него префиксы зарезервированы
за коробочными правилами. Суффикс должен начинаться с буквы или цифры.

Заменяется только начало `id`, а не все вхождения текста. Один запуск обрабатывает
один выбранный префикс; остальные правила в той же папке не включаются в результат.
Для другого префикса выполните отдельный запуск.

При запуске compare или bootstrap без параметра в интерактивном терминале
префикс запрашивается у пользователя. В скриптах и CI используйте `--custom-prefix`:
без терминала и без параметра команда завершится ошибкой, не выбирая префикс сама.

Bootstrap сохраняет префикс в `state.json` (schema 2). Analyze читает его автоматически,
повторный ввод не требуется. Его необязательный `--custom-prefix` только проверяет
совпадение с сохранённым значением и не меняет соответствие BASE. Для старых рабочих папок schema 1 без этого поля префикс выводится из сохранённых
соответствий custom → RV. Если соответствия неоднозначны, выводится ошибка.

### Демонстрация без реальных данных

В репозитории есть только синтетические правила. Создать демонстрационный пакет:

```sh
python examples/build_demo.py
rvision-rule-sync compare --custom-prefix SOC- --custom tests/fixtures/SOC-D-DEMO1.ro examples/SIEM/demo.roc
```

Ожидается `REVIEW_REQUIRED`, код выхода `2`: пример специально содержит отличия.
Синтетические правила предназначены для проверки утилиты, а не для импорта в SIEM.
[Пример отчёта](examples/report.md) показывает формат результата.

## Отчёт и статусы compare

```text
reports/<уникальный-id>/
├── report.md
├── results.json
├── packages.json
└── package-001/
    ├── CUSTOM/SOC-D-100.ro
    └── SIEM/RV-D-100.ro
```

Новый запуск создаёт новую папку. Предыдущие результаты не перезаписываются.
В diff строки `−` относятся к custom, строки `+` — к правилу из пакета.

| Статус | Значение в прямом сравнении |
|---|---|
| `NO_CHANGE` | Учитываемые блоки custom и RV совпадают после канонизации |
| `METADATA_ONLY` | Отличается только metadata |
| `REVIEW_REQUIRED` | Отличается логика, другое учитываемое поле или нарушена разметка маркеров |
| `ORPHANED` | Соответствующий RV отсутствует в конкретном пакете |

`id`, `rid`, `test` и `tests` исключены из сравнения. Номер версии не используется
как единственный признак изменения.

Прямое сравнение показывает **различия файлов**, а не авторство этих различий.
Без исторического BASE невозможно установить, где была ваша кастомизация,
а где обновление vendor. Поэтому compare не выполняет merge и не создаёт
кандидатов даже при `METADATA_ONLY`.

В JSON доступны `status`, `different_blocks`, `diffs`, `hashes`, `custom_regions`,
`marker_warnings`, `custom_prefix` и информация об источниках. `packages.json` связывает снимки
с пакетами и содержит количество проиндексированных RV-правил.

## Мои критичные изменения

Ставьте маркеры отдельными строками **внутри VRL**, без кавычек:

```yaml
on_correlate: !vrl |
  .device_vendor = "example"
  # начало моих изменений
  .groupedBy = ["example_custom_host"]
  # конец моих изменений
```

Допустимы несколько непересекающихся участков в одном правиле, в том числе внутри
`aliases/.../filter`. Отступы вокруг маркеров и CRLF поддерживаются; текст маркеров
должен совпадать с примером. Внешние YAML-комментарии парсер не сохраняет,
поэтому размещайте разметку внутри текстового блока, как показано выше.

В отчёте появляется раздел **«Мои критичные изменения»**: код, путь и номера строк
внутри текстового блока, включая строки маркеров. В compare блоки с отмеченными
фрагментами показываются первыми.

Разметка не исключает код из diff и не определяет соответствующий участок vendor.
Сами комментарии и код сохраняются. В analyze изменение vendor в блоке, содержащем
отмеченный критичный участок, требует review. Непарные и вложенные маркеры дают
`marker_warnings` и `REVIEW_REQUIRED`; если RV отсутствует, статус остаётся `ORPHANED`.
Маркеры внутри `test/tests` игнорируются.

## Дополнительно: BASE/OURS/THEIRS

Для безопасного автоматического переноса независимых изменений нужна исходная
коробочная версия, от которой сделана кастомная копия:

| Роль | Содержимое |
|---|---|
| BASE | Историческое RV-правило, изменения которого ещё не приняты в custom |
| OURS | Актуальное кастомное правило с выбранным префиксом |
| THEIRS | RV-правило из нового пакета |

```sh
rvision-rule-sync bootstrap \
  --custom-prefix SOC- \
  --workspace ./content \
  --base ./old-vendor \
  --custom ./my-rules \
  --baseline-verified

rvision-rule-sync analyze --workspace ./content ./SIEM/new-content.roc
```

`--base` и `--custom` принимают один `.ro`, каталог либо совместимый архив.
Bootstrap создаёт **новую** рабочую папку; существующую он не перезаписывает.
Флаг `--baseline-verified` означает, что вы подтверждаете происхождение custom от
переданного BASE. Без флага analyze требует review и не создаёт кандидатов.

```text
content/
├── base/RV-D-100.ro
├── custom/SOC-D-100.ro
├── state.json
└── runs/<id>/
    ├── BASE/
    ├── OURS/
    ├── THEIRS/
    ├── generated/
    ├── report.md
    └── results.json
```

| Статус | Значение в analyze |
|---|---|
| `NO_CHANGE` | Vendor не изменил учитываемые блоки относительно подтверждённого BASE |
| `METADATA_ONLY` | Vendor изменил только metadata без пересечения с custom; кандидат создан |
| `AUTO_MERGE` | Vendor изменил известные блоки независимо от custom; кандидат создан |
| `REVIEW_REQUIRED` | Пересечение блоков, критичный участок, неподтверждённый BASE, ошибка маркеров или изменённое неописанное поле; кандидата нет |
| `ORPHANED` | RV отсутствует в новом источнике; кандидата нет |

Правила merge:

- Единицы сравнения: `metadata`, `filter`, `aliases`, `select`, `group`, `ttl`,
  `throttle_time_sec`, `on_correlate`. Добавление и удаление блока учитываются.
- Один блок изменён обеими сторонами → review, даже если итоговый VRL совпал.
  Внутри VRL слияния по строкам нет. `aliases` сравнивается целиком.
- Отмеченный пользователем критичный блок защищён от автоматической замены vendor.
- `id` и `rid` всегда берутся из custom. `test/tests` не сравниваются и сохраняются
  из custom, включая отсутствие блока.
- `metadata` — один общий блок из `name`, `version`, `date`, `author`, `status`,
  `description`, `response`, `reference`, `references`, `incident_taxonomy`,
  `tags`, `data_source`, `known_false_positives` и явного `metadata`.
- Другие поля, включая `severity`, `model`, `type`, учитываются отдельно.
  Изменение vendor в неописанном поле требует review.

Analyze не меняет BASE/custom. Полный хеш BASE проверяет целостность файла,
включая тестовые данные. Структурные хеши и diff тестовые блоки исключают.

Кандидат — результат структурного слияния, а не подтверждение корректности детекта.
Блоки могут быть связаны логически, поэтому проверьте правило перед ручным импортом.
Автоматического `accept` нет. После принятия обновления создайте новую рабочую папку
через bootstrap с одобренным custom и соответствующим новым RV из THEIRS.
Старую папку сохраните для аудита. Для добавления нового custom-правила в analyze тоже нужен
BASE и новая регистрация; compare подхватывает новые custom-правила без этих шагов.

## YAML, канонизация и ограничения

SHA-256 считается по типизированному дереву с отсортированными ключами.
CRLF/CR нормализуются в LF. YAML-комментарии, отступы структуры, стиль кавычек
и порядок ключей не влияют на хеш. Типы значений, порядок списков и наличие ключей
значимы. YAML-комментарии и исходный визуальный стиль при генерации не сохраняются.

Все `!vrl` остаются текстом с тегом. Пробелы и комментарии **внутри VRL** не
удаляются: без VRL-парсера их нельзя надёжно отделить от содержимого строк.
Маркеры также остаются частью сравнения. Их поиск строковый: утилита не
разбирает синтаксис VRL и не отличает строку маркера внутри многострочного
литерала от комментария. Используйте точные строки маркеров только для разметки.

Используется ограниченный профиль YAML: `true/false` — булевы значения;
`on/off/yes/no` и даты читаются строками. Это сохраняет ключ `select.join.on`.
Неизвестные теги, повторные/нестроковые ключи, YAML-алиасы и чрезмерная вложенность
отклоняются. Дублирующиеся ID запрещены без учёта регистра, чтобы избежать
перезаписи файлов на разных ОС.

`.roc` должен быть ZIP/TAR либо сжатым TAR, поддерживаемым стандартной библиотекой
Python на вашей системе. Неизвестные, зашифрованные и повреждённые форматы завершаются
ошибкой. Предельный размер `.ro` — 16 MiB; архив — до 20 000 элементов и 512 MiB
распакованного содержимого. Ссылки, выход за путь распаковки и повторные пути запрещены.
Это ограничения входных данных, а не изолированная среда для запуска враждебных файлов.

## Коды выхода

| Код | Значение |
|---|---|
| `0` | Команда выполнена, нерешённых статусов нет |
| `1` | Ошибка входных данных или чтения/записи |
| `2` | Есть `REVIEW_REQUIRED` или `ORPHANED`; отчёт создан |

Argparse также возвращает `2` при ошибке аргументов — в этом случае отчёт не создаётся.
`METADATA_ONLY` даёт `0`. В compare это означает завершённое сравнение,
а не обновление custom.

## Разработка и тесты

```sh
python -m pip install -e '.[test]'
python -m pytest -q
```

Обычный набор тестов использует только синтетические примеры и не требует
доступа к SIEM, сети или коробочной экспертизе. Архивы для тестов создаются
во временных каталогах. Проверяются парсинг, канонизация, статусы, merge,
защита критичных участков, игнорирование test/tests, CLI и обработка ошибок.

Дополнительные локальные регрессионные проверки доступны при передаче приватных данных:

```sh
python -m pytest -q --private-fixtures /path/to/private-fixtures --private-custom-prefix CUSTOM-
```

В каталоге используются нейтральные имена: `vendor-base.ro`, `custom.ro`,
`vendor-current.ro` (новый RV, извлечённый из пакета) и `content.roc`.
`--private-custom-prefix` задаёт префикс правила из `custom.ro` (по умолчанию `CUSTOM-`).
Эти файлы не входят в репозиторий. Набор проверяет ожидаемые отличия локальной
регрессионной пары, поэтому для другого набора входов может потребоваться
скорректировать ожидаемые изменения в `tests/private/test_real_rules.py`.
Без флага приватные тесты не собираются. Проверки не исполняют встроенные VRL-тесты
правил в движке SIEM.

[Результаты проверки этой версии](VALIDATION.md).

## Состав репозитория и пользовательские данные

```text
rvision_rule_sync/    # парсер, сравнение, CLI, работа с архивами и маркерами
examples/            # генератор демопакета и синтетический отчёт
tests/              # тесты и синтетические fixtures
custom/              # ваши кастомные правила, исключены из Git
SIEM/                # ваши пакеты, исключены из Git
```

Реальные правила, пакеты экспертизы, локальные рабочие папки и созданные отчёты
не включены в публичную поставку. `.gitignore` исключает их по умолчанию;
исключение сделано только для синтетических `.ro` в `tests/fixtures/`.

Игнорирование test/tests при сравнении не удаляет их из исходных файлов и снимков:
отчёты, JSON и снимки могут содержать события, имена узлов и локальные пути.
Проверяйте содержимое перед самостоятельной публикацией результатов.
