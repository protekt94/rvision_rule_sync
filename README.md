# rvision-rule-sync 0.3.0

Локальная утилита Python 3.10+ для сравнения кастомных правил R-Vision с пакетами
SIEM. Без LLM и SIEM API; VRL хранится как текст и не исполняется.

## Установка

Откройте терминал в распакованной папке проекта:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[test]'
```

Windows PowerShell: вместо `source` выполните `.venv\Scripts\Activate.ps1`.
Вместо `python3` можно использовать `py -3`.

## Основной режим: custom против SIEM/*.roc

Складывайте актуальные кастомные правила в `custom/`, новые пакеты в `SIEM/`:

```text
rvision-rule-sync/
  custom/
    VI-D-971.ro
    VI-D-996.ro
  SIEM/
    SIEM_Content_CIMv2_22092026.roc
  reports/
```

Запуск из папки проекта:

```sh
rvision-rule-sync compare
```

Старые custom, BASE и bootstrap **не нужны**. Новые VI автоматически подхватываются.
Если правило изменили в SIEM, замените его актуальным экспортом в `custom/`.

Другие пути или конкретный пакет:

```sh
rvision-rule-sync compare --custom ./custom "SIEM/*.roc"
rvision-rule-sync compare --custom ./custom ./SIEM/new.roc --output ./reports
```

Windows-шаблон `"SIEM\*.roc"` также поддерживается. Файлы `.ro` ищутся рекурсивно;
сопоставление по полю `id`: `VI-<suffix>` → `RV-<suffix>`, независимо от имени файла.
Все `.roc` непосредственно в папке SIEM обрабатываются отдельно. При нескольких
пакетах каждое custom сравнивается с каждым пакетом; правила пакетов не смешиваются,
«самый новый» пакет автоматически не выбирается. Чтобы проверить только один,
укажите его путь или оставьте в SIEM только его.

Каждый запуск выводит путь к `reports/<уникальный-id>/report.md`. Рядом находятся
`results.json`, `packages.json` и снимки `package-NNN/CUSTOM/`, `package-NNN/SIEM/`.
В diff знак − означает custom, знак + — RV из пакета.

| Статус compare | Значение |
|---|---|
| NO_CHANGE | Файлы совпадают после канонизации, кроме id/rid и test/tests |
| METADATA_ONLY | Различается только metadata |
| REVIEW_REQUIRED | Различаются логика или другие учитываемые поля |
| ORPHANED | Ожидаемый RV отсутствует в конкретном пакете |

Это различия текущих файлов, а не доказательство новых изменений vendor.
Без BASE нельзя отделить ваши намеренные правки от обновления vendor.
Поэтому compare не создаёт кандидатов и не перезаписывает custom, даже при
METADATA_ONLY. Старые отчёты не перезаписываются.

## Пример на комплектных данных

Реальные файлы находятся в `tests/fixtures/`:

```sh
rvision-rule-sync compare --custom ./tests/fixtures/VI-D-971.ro \
  ./tests/fixtures/SIEM_Content_CIMv2_22092026.roc
```

Для этой пары: REVIEW_REQUIRED, различаются metadata и on_correlate; test/tests игнорируются.
Готовый пример — `example-direct-report/report.md`.

## Разметка моих критичных изменений

Внутри многострочного VRL ставьте маркеры отдельными строками, **без кавычек**:

```yaml
on_correlate: !vrl |
  .device_vendor = %virus_detected.device_vendor
  # начало моих изменений
  .groupedBy = ["device_hostname"]
  .dst_hostname = %virus_detected.dst_hostname
  # конец моих изменений
```

Это комментарии внутри VRL (с тем же YAML-отступом, что и код). Внешние комментарии
YAML до/после `on_correlate: !vrl |` парсер не сохраняет, поэтому ставьте их внутри
блока. Маркер распознаётся по точному тексту отдельной строки; окружающие пробелы
и CRLF допустимы. Кавычки вокруг всей строки маркера не нужны.

Можно отмечать несколько непересекающихся участков, в том числе во вложенных
`aliases/.../filter`. В отчёте появится раздел «Мои критичные изменения» с кодом,
путём и номерами строк внутри текстового блока. В прямом diff блоки с отмеченными
участками показываются первыми и подписываются. В JSON это `custom_regions`.
Содержимое и сами комментарии сохраняются в исходном тексте и кандидатах.

Разметка **не исключает код из сравнения** и не определяет, где именно vendor
изменил соответствующий участок. Полный diff остаётся доступен. Без BASE авторство
различий не устанавливается. Если обе стороны изменили один VRL-блок, analyze
по-прежнему требует review. Маркеры не разрешают перезаписать критичные правки.

Непарные и вложенные маркеры дают `marker_warnings` и REVIEW_REQUIRED, если RV
найден; при отсутствующем RV сохраняется ORPHANED. Разметка в test/tests игнорируется.
Пример с добавленной разметкой к копии реального VI: `examples/marked-custom/VI-D-971.ro`;
его отчёт — `examples/markers-report.md`. Оригинальный fixture не изменён.

## Дополнительный режим: BASE/OURS/THEIRS

Нужен только для трёхстороннего анализа и безопасного слияния.
Обычному compare он не требуется.

```sh
rvision-rule-sync bootstrap \
  --workspace ./content \
  --base ./tests/fixtures/RV-D-971.ro \
  --custom ./tests/fixtures/VI-D-971.ro \
  --baseline-verified
rvision-rule-sync analyze --workspace ./content \
  ./tests/fixtures/SIEM_Content_CIMv2_22092026.roc
```

`--base` и `--custom` принимают один .ro, каталог или архив. Флаг
`--baseline-verified` подтверждает историческое происхождение custom от BASE.
Без него анализ требует review. Не заменяйте исторический BASE новым пакетом
без принятия соответствующего обновления. Bootstrap создаёт только новую папку.

```text
content/
  base/RV-D-971.ro
  custom/VI-D-971.ro
  state.json
  runs/<id>/
    BASE/
    OURS/
    THEIRS/
    generated/
    report.md
    results.json
```

Analyze не меняет BASE или custom. Хеш BASE проверяется перед анализом.

| Статус analyze | Значение |
|---|---|
| NO_CHANGE | Vendor не изменился относительно подтверждённого BASE |
| METADATA_ONLY | Vendor изменил только metadata, пересечения с custom нет; кандидат создан |
| AUTO_MERGE | Известные блоки vendor изменены без пересечения с custom; кандидат создан |
| REVIEW_REQUIRED | Пересечение, неподтверждённый BASE или неизвестные изменённые поля; кандидата нет |
| ORPHANED | RV отсутствует в новом источнике; кандидата нет |

Единицы diff/merge: metadata, filter, aliases, select, group, ttl,
throttle_time_sec, on_correlate. aliases сравнивается целиком. Верхнеуровневые
блоки test и tests исключены из сравнения, хешей блоков и переноса изменений.
Они остаются в исходных снимках и сохраняются из custom при слиянии. Полный
контрольный хеш файла BASE по-прежнему проверяет целостность всего файла.
Если обе стороны изменили один блок, нужен review — даже если обе получили
одинаковый VRL. Добавление и удаление блоков учитываются.

Metadata объединяет name, version, date, author, status, description, response,
reference, references, incident_taxonomy, tags, data_source, known_false_positives
и явный metadata. Это единый блок: разные его поля тоже могут дать пересечение.
Неописанные поля (включая severity, model, type) учитываются отдельно;
изменения vendor в них требуют review. id/rid всегда сохраняются из custom.

Структурно независимые блоки могут быть связаны логикой. Кандидат следует проверить
перед ручным импортом в SIEM. Автоматического accept нет: после принятия обновления
создайте новую рабочую папку через bootstrap с одобренным custom и соответствующим
RV из THEIRS. Старую папку сохраните для аудита. Новое VI для analyze требует BASE
и регистрации через bootstrap; для compare достаточно добавить файл в custom/.

## Канонизация, форматы и ограничения

Поддерживаются ZIP, TAR и сжатые TAR независимо от расширения .roc.
Неизвестный формат вызывает ошибку. Архивы ограничены 20 000 элементами и
512 MiB содержимого. Ссылки, выход за путь распаковки и повторные пути запрещены.
Повторные ID, неизвестные YAML-теги, повторные/нестроковые ключи и циклы отклоняются.

Хеши SHA-256 считаются по типизированному дереву с отсортированными ключами.
LF/CRLF/CR нормализуются; YAML-комментарии, отступы структуры, стиль кавычек и
порядок ключей не влияют на хеш. Типы, порядок списков и наличие ключей значимы.
Все !vrl сохраняются как текст с тегом, включая вложенные filter и assertion.
Пробелы/комментарии внутри VRL не удаляются, поскольку могут быть частью строк.
Исходные YAML-комментарии и визуальный стиль при генерации не сохраняются.

Ключ on сохраняется строкой. Булевы значения — true/false; on/off/yes/no и даты
читаются строками. Это ограниченный профиль YAML, не полная реализация YAML 1.2.
Версия правила не используется как единственный признак изменения.

Коды выхода: 0 — нет нерешённых статусов; 2 — review/orphaned; 1 — ошибка данных.
Ошибки синтаксиса аргументов argparse также дают 2. Альтернативный запуск:
`python -m rvision_rule_sync compare`.

## Проверки

```sh
pytest -q
```

Тесты используют реальные RV-D-971.ro, VI-D-971.ro и .roc из беседы,
а также синтетические изменения их копий. RV-D-971.package.ro извлечён из .roc.
В исходной тройке vendor изменил только точки в known_false_positives, сохранив
версию 1.0.3. Analyze выдаёт REVIEW_REQUIRED из-за пересечения metadata с custom.
Пример — `example-report/report.md`. Pytest проверяет утилиту, а не исполнение VRL
в движке SIEM. Данные событий и отчёты могут содержать инфраструктурные сведения.
